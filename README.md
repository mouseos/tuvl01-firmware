# TUVL01 firmware

日本アンテナのi-dio Wi-Fiチューナー（TUVL01）を、地上デジタル放送（UHF 13〜52ch / フルセグ・ワンセグ）のWi-Fi受信用チューナー化するカスタムファームウェアです。
起動するとWi-Fi APが立ち上がり、TVTest等から選局・TSストリーム受信が行えます。

## 特徴・仕様

- **完全スタンドアロン起動**: 電源投入後約25秒でAP（SSID: `TUVL01` / 暗号化なし）が自動起動。PC接続やUART操作は不要です。
- **フルセグ / ワンセグ対応**: フルセグ転送レート約17Mbps。
- **BonDriver同梱**: TVTest専用の `BonDriver_TUVL01.dll` からWi-Fi経由でチャンネルスキャン・選局・ストリーム制御可能。
- **プレーヤー非依存**: 独自UDPプロトコル（TTS1 / TCT1）を採用し、クライアント用C言語実装を `client/` に収録。他OSやスマホアプリへの移植も容易です。
- ※スクランブル放送の視聴・復号には別途B-CAS環境が必要です。

### LEDインジケータ
- **赤点灯**: 起動処理中
- **緑点滅（遅）**: 起動完了・待機中（クライアント未接続）
- **緑点灯**: クライアント接続中（ストリーム受信中含む）
- **赤緑高速点滅**: 起動・動作エラー

## 導入手順（SPI書き換え）

基板上のSPI NORフラッシュ（S25FL164K / 8MiB）をプログラマ等で直接書き換えます。分解が必要です。

**読み出し・書き込み・ベリファイは、次のいずれかの方法で行ってください。この条件を満たさないと失敗します。**

- 基板上で作業する場合は、USBコネクタ付近にある隠しリセットボタン **SW3を押し続けたまま**読み出し・書き込み・ベリファイを行います。
- または、SPIフラッシュのチップを基板から取り外し、プログラマで読み出し・書き込み・ベリファイを行います。作業後にチップを基板へ戻します。

バッテリーは接続したままでも、外した状態でも作業できます。

1. **バックアップ取得**: 作業前に元のフラッシュ内容を必ずバックアップしてください（ベリファイ推奨）。
2. **書き込みイメージの準備**:
   - リリースの `tuvl01-spi-8MiB.bin` を使用（`SHA256SUMS.txt` でハッシュ確認）。
   - または下記ビルド手順で独自ビルド。
3. **ROM焼き**: `tuvl01-spi-8MiB.bin` をフラッシュ全体（8MiB）に書き込み、ベリファイを実施。
4. **起動確認**: 基板を戻して電源投入。約25秒後にLEDが緑点滅になり、SSID `TUVL01` が見えれば成功です。

※純正ファームに戻す場合は、事前に退避したダンプを書き戻してください。

## TVTestでの利用手順

1. PCのWi-Fiを `TUVL01` に接続（DHCPで `192.168.74.2` が割り当てられます）。
2. `BonDriver_TUVL01.dll` をTVTestフォルダに配置。
3. `TVTest.exe /d BonDriver_TUVL01.dll` を起動し、チャンネルスキャンを実行。
   - チューニング空間: `UHF`（フルセグ） / `UHF (1seg)`（ワンセグ）
4. ※WindowsファイアウォールでTVTestのUDPポート4202受信が許可されている必要があります。

## ビルド方法

Ubuntu 24.04 または WSL2（Ubuntu）環境でビルドします。

```sh
sudo apt-get install build-essential binutils-sh-elf libgmp-dev libmpfr-dev libmpc-dev python3 git
git clone --recurse-submodules https://github.com/mouseos/tuvl01-firmware.git
cd tuvl01-firmware
python3 tools/bootstrap.py
python3 tools/build_release.py --out release
```

`release/` ディレクトリに以下のファイルが生成されます：
- `tuvl01-spi-8MiB.bin`: SPI書込用フルイメージ
- `SHA256SUMS.txt`: ハッシュリスト
- `BonDriver_TUVL01.dll`: TVTest用BonDriver（ビルド済みの場合）

※開発・デバッグ用イメージ（UART制御前提）をビルドする場合は単に `make` を実行してください。

## 通信仕様（Wi-Fi UDP）

| 項目 | 設定値 |
| --- | --- |
| AP設定 | SSID: `TUVL01` / 2.4GHz / 認証なし / 1クライアント |
| IP割当 | デバイス: `192.168.74.1` / クライアント: `192.168.74.2` (DHCP) |
| 制御ポート | UDP `192.168.74.1:4200`（コマンド / レスポンス） |
| キープアライブ / エコー | UDP `192.168.74.1:4201` |
| TSストリーム | UDP `192.168.74.1:4202` → `192.168.74.2:4202` |

### ストリームフォーマット（TTS1）
各UDPパケットは16バイトヘッダ + 188バイトTSパケット（1〜7個）で構成されます。ビッグエンディアン。

- `0x00` (4B): マジック `TTS1`
- `0x04` (4B): パケットシーケンス番号（STARTごとに0リセット、1ずつ加算）
- `0x08` (4B): TSパケット通し番号（STARTごとに0リセット）
- `0x0C` (4B): フラグ（bit0: FIFO再同期フラグ）
- `0x10`〜: TSデータ本体（188 * n バイト）

※ストリーム開始（START）ごとにシーケンス番号は0に初期化されます。受信側でパケット破棄判定を行う際はストリーム境界（seq=0, index=0）を考慮してください。

### コントロールコマンド（TCT1）
UDPポート4200宛てに送信。ヘッダは `TCT1` (4B) + コマンド (1B) + 予約 (1B) + 要求ID (2B) + パラメータ。
応答はコマンドの最上位ビット（0x80）が立ち、5バイト目にステータスコード（0: 成功）が格納されます。

- **HELLO (0x01)**: バージョン・機能ビット等の照会
- **START (0x02)**: ストリーム送信開始
- **STOP (0x03)**: ストリーム送信停止
- **STATUS (0x04)**: 現在のステータス取得（選局ch、ロック状態等）
- **KEEPALIVE (0x05)**: セッション維持（5秒無通信で自動停止）
- **TUNE (0x06)**: 選局要求（ch: 13〜52 / mode: 0=フルセグ, 1=ワンセグ）

### MN885521内部プログラム窓の実験用診断

`python tools/uart.py tuner-program-port --port COMx --log logs/program-port.bin` は、Main1の `F3=E0, F4/F5=0298` を確認し、純正のパッチ転送状態 `F3=E3` でF6/F7を各8バイト読み、F3を元に戻します。UARTのCtrl-Aでも実行できます。アドレスとパッチデータは書き込みません。復帰失敗は `restore-failed` として報告します。

これは読出し経路を調べる実験用機能です。返却値をIQやプログラムメモリと同定しておらず、連続サンプリングも行いません。実行時にはTS送信を停止し、内部プログラムの動作状態を一時的に変更するため、受信を再開する際は再選局してください。検証にはRAMへアップロードしたイメージを使い、Flash保存は不要です。

TUVL01実機では、通常状態E0と転送状態E3のどちらでもF6は最後のパッチ書込みバイト `2B` を繰り返し、F7は `00` でした。この方法でIQまたはアドレスが進むプログラム読出しは確認できていません。

`python tools/uart.py tuner-program-burst --port COMx --log logs/program-burst.bin` は、同じ状態確認の後、Main1 D6..DBの6バイト連続読出しを単発読出しと比較します。一致した場合だけ、E0/E3それぞれでF6/F7起点の8バイトを読み、F3とF4/F5の復帰を確認します。UARTの `*` でも実行できます。読出し長は最大8バイトに制限し、受信区間は割込みを抑止した有限回数のポーリングを使います。SH726Aマニュアル19.7.2/19.7.3の注意事項に対応するため、この区間でRTOSの待機処理を呼びません。

実機で4回実行し、通常レジスタの一致と復帰を確認しました。E3のF6起点では `2B 00 44 03 C0 00 00 01`、F7起点では `00 44 03 C0 00 00 01 00` が返った例があり、隣接レジスタの自動増分と整合します。後続の一部レジスタは値が変動します。この連続読出しでも、IQや内部プログラムを搬出する経路は確認できていません。実行時のTS停止と再選局、RAM検証の条件は上記の単発診断と同じです。

以前のTab割当ては既存のTS pipelineコマンドと衝突し、内部窓診断の前にpipeline設定コマンドも実行していました。上記の4回はこの旧版での確認です。新しい割当ては `*`、Tabは従来のpipeline設定専用です。ホストツールとファームを同じ版で使用してください。

`python tools/uart.py tuner-program-release --port COMx --log logs/program-release.bin`（直接UARTなら `.`）は、通常E0、転送E3、メーカー解除E2の順でF6/F7を単発8回と8バイト連続で比較します。HTV31 2.44のメーカーライブラリでは、`tuner_ini_pseq1_release`（ELF `7078..70D2`）とTNCTL解除処理がF3 bit1を1、bit0を0にします。観測した上位ビットならE2で、TUVL01のE0とは異なります。ただしbit1の意味やメモリ読出しを許可する値かどうかは不明です。

通常レジスタの単発・連続読出しの一致を先に確認し、F3だけを一時変更します。解除時はE3を書いてbit1を1にした後、E2を書いてbit0を0にします。要求値と読戻し値を記録し、実機で観測したE3要求後のE1、E2要求後のE0も、その観測状態の有限長読出しとして比較します。それ以外の不一致なら中止します。bit1が自己消去するか、書込み専用か等の意味は未確定で、書込み値と読戻し値を同一とは扱いません。アドレス・データ・リセットには書き込まず、各モードの後でアドレス不変、終了時にF3とF4/F5の復帰を確認します。`read-restored-unclassified` は診断読出しと復帰の成功を表し、IQ取得の成功ではありません。TS停止、再選局、RAM検証の条件は上記と同じです。

旧版（commit `15b8d1b`）の実機追跡では3回とも、E0はE0を読戻し、E0から直接E2を書いた後はE0を読戻しました。この版は不一致で中止し `read-failed-restored` を報告し、E2/E3のデータ取得には進んでいません。E0の単発F6は `2B` 反復、F7は `00` 反復で、連続読出しは隣接レジスタの自動増分と整合します。F3とアドレス0298の復帰、その後の通常再初期化・選局の `ready` とSPI FIFO応答を確認しました。E2が読戻せない理由（自動変化、ビットの読出し仕様、状態遷移の条件等）は未確定です。メーカー解除処理の直前は転送状態であり、旧版のE0から直接E2への変更と同一条件とは限りません。

現在のメーカー順序による実機比較は3回成功し、要求E0/E3/E2に対して読戻しはE0/E1/E0でした。全段階でF6の単発8回は `2B`、F7は `00` の反復で、連続読出しも隣接レジスタと整合しました。bit1を0として読戻すことは確認できましたが、その意味と、IQまたは内部プログラムメモリを読む経路は未確定です。設定・アドレスの復帰、通常再初期化・選局の `ready` とSPI FIFO応答を確認しました。

### STM出力選択の意味

HTV31 2.44のメーカー試験アプリ `fullseg_test` は、`cfg_stm` を「Status Terminal Monitoring configuration」と表示します。AArch64の表示処理（ELF `9280..94DC`）にある表とインデックス演算を確認しました。これは試験アプリの説明で、チップの正式な全レジスタ仕様ではありません。

| 選択値 | STM0SEL / STM1SEL | STM_TMCCSEL | STM_ERRSEL |
| --- | --- | --- | --- |
| 0 | STMD[0] / STMD[1] 汎用出力値 | TMCCERR | Packet error PERR |
| 1 | ISYNC | L-level | L-level |
| 2 | ERR or STM_ERR | CDFLG | Error-free NERRF |
| 3 | STM_TMCC | EMGFLG | For testing use |
| 4 | SYNC | PART | PERR of hierarchy layer A |
| 5 | ERR | AC_EMG | PERR of hierarchy layer B |
| 6 | TMCC | AC_SDSCERR | PERR of hierarchy layer C |
| 7 | INT | AC_CRCERR | L-level |

APIのpacked値では各選択が順にbits 2..4、5..7、8..10、11..13です。メーカーライブラリがこれをMain1 E5/E6またはMain2 F9/FAへ変換します。モードごとに幅・配置が異なり、ワンセグのSTM_ERRSELは1ビットのため、この表示表の全値が有効とは限りません。上記は同期・割込み・エラー等の状態端子の選択で、I/Qサンプルを出す設定の根拠は得られていません。`For testing use` の内容は未確定です。この表示表を理由とする追加の実機設定変更はしていません。

同系列メーカーライブラリのピン試験は、D7/DA/DB/E7を設定する前にMain2 E8/F8の下位4ビットを0、Sub ACのbit2を1に変更します。通常のTUVL01 SPI設定はE8=`02`、F8=`01`で、試験時とは出力インターフェース設定が異なります。下記の表示表からE8の値0はTS Serialと判明しました。試験値をSPI経由のIQ出力設定として使用できる根拠と、TUVL01での実際の試験出力ピンは未確認です。

HTV31の通常受信アプリにも、選局成功後にE8の下位4ビットだけを0にする経路があります。同機のデバイスツリーには専用のTS CLK/EN/DATA端子があり、別のTS出力経路と整合します。E8の値0をIQ専用モードと解釈する根拠はありません。このHTC側の端子番号をTUVL01へ移植することもできません。

### 出力インターフェースとGPIOの選択

HTV31 2.44のメーカー試験アプリのポート設定表示（AArch64 ELF `B28C..B7F0`）と、メーカーライブラリの `cfg_pctl` を照合しました。TPMの16要素の表はELF `224A8`にあり、`R_AARCH64_RELATIVE` の再配置情報から文字列を復元しています。

| TPM値（Main2 E8 bits 0..3） | メーカー表示 |
| --- | --- |
| 0 | TS Serial |
| 1 | TS Parallel |
| 2 | I2C/SPI(slave) |
| 3 | I2C/SDIO |
| 4 | I2C/Diversity(Master) |
| 5 | I2C/Diversity(Slabe)（原文表記） |
| 6..15 | reserve |

Main2 F8 bits 0..1はTSSELで、0=`TS(DVB-SPI) Serial`、1=`SPI`、2=`TS like SPI`、3=`output Low`です。F8 bits 2..3はTSERRSELで、0=`TSERR`、1=`SYNC`、2=`TMCCERR`、3=`output Low`です。通常値E8=`02`・F8=`01`はTPM=2・TSSEL=1・TSERRSEL=0に対応します。

| 選択項目 | レジスタ | 値0 | 値1 |
| --- | --- | --- | --- |
| GPIO1SEL | Sub AC bit1 | GPIO[1] | STM1 |
| GPIO0SEL | Sub AC bit0 | GPIO[0] | STM0 |
| GPIO7SEL | Sub AC bit2 | TSERR | GPIO[7] |

メーカーAPIのpacked値のbits 15/16/17を、それぞれSub AC bits 1/0/2へ変換する処理は、ARM32版とAArch64版（`cfg_pctl` ELF `B3B0`）で確認しました。以前のモード0の端子観測はTS Serialへの切替試験であり、ピン試験のSub AC bit2=1はGPIO7選択です。これらは出力インターフェース・状態端子の設定で、IQ信号源を選ぶ証拠は得られていません。UARTのみの実機環境では、チップの端子名と既存PD4〜PD7配線の対応や高速波形は未確認です。この表の解析による追加の実機設定変更はしていません。

### TSデータ出力の選択

HTV31 2.44のメーカー試験アプリのTS設定表示（AArch64 ELF `9F8C..AD60`）と、同版のメーカーライブラリの `cfg_tsout` を照合しました。フルセグとワンセグでは、同じ名前の選択項目でも説明が異なります。

| 値 | SDOSEL_F（Main1 D6 bits 4..5、mask `30`） | SDOSEL_S（Main2 00 bits 4..5、mask `30`） |
| --- | --- | --- |
| 0 | normal TS | TS output |
| 1 | demodulated TS | Viterbi/RS復号後のBER測定データ、シリアルクロック停止時は0を出力 |
| 2 | decoded TS | Viterbi/RS復号後のBER測定データ |
| 3 | reserve | prohibit |

フルセグの表示ラベルだけから、復調・復号の正確な内部段階やサンプル形式は確定できません。これらの選択値をI/Qのmux値として使える根拠は得られていません。

TUVL01実機の既存RAMファームで、UARTのレジスタ診断からMain1 D6のmask `30`だけを0→1→2→0と変更し、各回128個の188バイト枠を既存のポーリングSPI取得・UART出力で保存しました。D6は `00/10/20/00` を読戻し、UART輸送CRCと元の選択値への復帰を確認しました。Flash変更はありません。

ただし、通常設定も含めてTEIは `127/128/127/127` 個、adaptation errorは `56/57/39/49` 個でした。通常再初期化・14ch再選局後も128個すべてにTEIがあり、既存品質診断のLayer-A/B PER生カウントはそれぞれ分子と分母が等しかったため、正常受信の基準データを得られていません。全枠の先頭が `47` であることや輸送CRC一致は、有効なTSやIQの証明ではありません。今回確認できたのは設定読戻し、有限長搬出、設定復帰までで、SPIデータが選択に追従するかとIQ取得は未確認です。

`cfg_tsout` group 3はMain2 F0..F7のシリアル出力設定です。試験アプリにはCKRAT、DTLEN、TDTF、WDLEN、DTDLY、PWDTH、FSTRT、FSPOL、CYCLE、CKINIT、PRTYEN、SPIFIFO等として表示されます。特にMain2 F2はCKRATであり、Main1/Subのプログラム窓とは区別します。I/Q形式やサンプルレートを設定する項目だとは確認していません。

### 試験用ラベルと復号・端子制御の区別

メーカー試験アプリのTS表示と `cfg_tsout` のバンク・バイト配置を照合し、次の項目を確認しました。

| 項目 | フルセグのレジスタ | メーカー表示 |
| --- | --- | --- |
| ERRSEL_F | Main1 DA bits 3..5、mask `38` | 0=TMCCERR、1=Low output、2=CDFLG、3..7=For testing use |
| TRSOFF_F | Main1 37 bit3、mask `08` | 0=RS decoding ON、1=RS decoding OFF |
| EI_F | Main1 37 bits 1..2、mask `06` | Specifies the error indicator bit |
| DENOFF_F | Main1 D7 bit4、mask `10` | データ有効端子の出力/Low |
| PCKOFF_F | Main1 D7 bit5、mask `20` | パケットクロック端子の出力/Low |
| TCKOFF_F | Main1 D7 bit6、mask `40` | TSクロック端子の出力/Low |
| TSDOOFF_F | Main1 D7 bit7、mask `80` | TSデータ端子の出力/Low |

ERRSEL_Fの試験用値はエラー出力端子の選択表にあります。内容は未確定で、IQのデータ出力選択とは確認していません。Main1 37はRS復号のON/OFFとエラー表示を含み、RS復号をOFFにできることからADCサンプルやIQを読めるとは判断できません。

以前のメーカーpin testで使ったD7のmask `70`はDENOFF/PCKOFF/TCKOFFの3ビットです。TSデータ端子のTSDOOFF（bit7）はこのマスクに含まれません。端子制御とデータ信号源の選択を区別します。この表示表の照合による追加の実機書込みはしていません。

メーカーAPIの `tunerx_create_tdc` も調べました。ARM32版は28バイト、AArch64版は40バイトを `malloc` し、固定の初期値を格納して返します。関数内にレジスタ読出しや波形の取得処理はありません。名称にcapture bufferの意味を推測してIQ取得APIと扱う根拠は得られていません。これはこの関数の処理についての確認で、他の経路でのデータ取得を否定するものではありません。

### UARTだけで出力端子を観測する診断

RAMへ新しいイメージをアップロードし、通常の初期化・選局・TS出力設定を済ませてから実行します。RSPI端子の初期化には `python tools/uart.py ts-probe --port COMx --log logs/ts-probe.bin` を使えます。

```
python tools/uart.py tuner-pin-capture --port COMx --log logs/pins.bin
python tools/pin_capture.py logs/pins.bin
```

UARTのバッククォート（ASCII `60`）でも実行できます。TS送信を停止し、DMA0/1とRSPI1が停止していること、端子設定が既知の `PDCR1=2222` であることを確認します。PD4〜PD7をすべて入力にして、通常設定 `E8[3:0]=2` と `0` を各512点記録します。変更するチップ設定はE8の下位4ビットだけで、F8やピン試験レジスタは変更しません。E8/F8の復帰確認後にMCU端子設定を戻し、RAM内の記録をUARTへ出力します。復帰に失敗した場合は端子を入力のまま残し、`restore-failed-inputs-retained` を報告します。

値のbit0〜3はPD4〜PD7です。タイムスタンプはGPIO読出し直前のCMTカウント（公称4.5 MHz）で、ソフトウェア処理や割込みによる間隔変動を含みます。高速な信号は見落とすため、変化が観測されなくても出力なしとは断定できません。これは端子状態の比較診断で、IQ取得、均一サンプリング、信号周波数の測定は未確認です。実行後の受信再開には再選局してください。

TUVL01実機で3回実行し、各回とも両モードの512点すべてが `0F`（PD4〜PD7すべてHigh）でした。初回の512点の観測幅は通常設定で5638カウント、モード00で5636カウント（公称約1.25 ms）、間隔中央値は11カウントでした。設定復帰、UART応答、再初期化・選局の `ready`、既存SPIのTS FIFO応答まで確認しました。`*` の内部窓診断も復帰に成功し、診断区間でpipelineコマンドの出力はありませんでした。今回の短い観測では、モード00から既存SPI配線へ信号を出す経路は確認できていません。

### メーカーのピン試験レジスタ設定の比較

同系列の `tunerx_chkpin` case 1/2にあるレジスタ設定を使い、UARTだけで端子を比較する実験です。通常のフルセグ設定（Main2 F2=`04`、Main1 ED=`16`、E8下位4ビット=`2`、F8下位4ビット=`1`、E7の試験ビットが0）が前提です。上記と同様、RAMアップロード後に選局・TS設定・RSPI初期化を済ませて実行します。

```
python tools/uart.py tuner-pin-test --port COMx --log logs/pin-test.bin
python tools/pin_capture.py logs/pin-test.bin --test
```

直接UARTへ `-` を送っても実行できます。PD4〜PD7を入力にしてから、Main2 E8/F8下位4ビットを0、Sub AC bit2を1、Main1 D7のmask `70`を`70`、DAのmask `38`を`08`にします。メーカーの割込み停止処理に対応するDC=`00`、DD下位4ビット=`0`も含めます。case 1はDB=`00`とE7のmask `71`=`31`、case 2はDB=`F9`とE7のmask `71`=`21`です。各変更の読戻しを確認してから各512点を記録します。

9レジスタの変更前値を保存し、試験停止、出力設定、割込み許可の順に変更したビットを戻します。対象外のビットは現在値を維持します。復帰確認に失敗した場合はMCU端子を入力のまま残します。メーカー処理には、選局済みの場合に先に `tuning(0,13)` を呼ぶ分岐もあります。モード表では引数0のラベルは `UF`、状態コードは `1321` です。この診断コマンド自身は再選局せず、既存の選局を維持するため、メーカー関数全体をそのまま再現するものではありません。

実機では通常の14chで3回、既存のプロファイル経路で13chへ再選局して1回実行しました。全4回、両caseとも全512点が `0F` で、既存SPI端子上の試験出力は確認できませんでした。14chでの観測幅は各case 5509 CMTカウント（公称約1.22 ms）、13chで9173（約2.04 ms）。レジスタ復帰と、その後の通常再初期化・選局の `ready`、SPI FIFO応答を確認しました。ソフトウェア観測の速度と間隔は一定ではなく、試験の出力ピン、波形、IQとの関係は未確定です。

### メーカーのTSパターン生成機能

同じ `chkpin` のmode 3は、メーカー試験アプリでTS test pattern outputと表示されます。アプリのAArch64 PLT呼出しと、ARM32/AArch64ライブラリのレジスタ設定を照合しました。

| コマンド | mode 3のpacked引数 | メーカーの説明 |
| --- | --- | --- |
| pat1 | `00000003` | 416 kbps、going round、204 byte |
| pat2 | `00000017` | 2.29 Mbps、ALL-AA、204 byte |
| pat3 | `0000002B` | 8.11 Mbps、ALL-FF、204 byte |
| pat4 | `0000003F` | 18.26 Mbps、ALL-00、204 byte |
| pat5 | `0100000B` | 612 kbps、going round、204 byte、PID=0 |

`bw13` の任意設定は、固定bit0=1、bit1=188/204 byte、bits2..3=ビットレート、bits4..6=round/AA/FF/00/nullの指定です。packed bit24=0ではMain1 E7の全バイトへ設定されます。bit24=1の `bw1` はMain2 C2/C3/C4へパターン等と13ビットPIDを設定します。これらのビットレートはメーカーのTS生成ラベルで、IQサンプルレートではありません。

mode 3は最初にTPM=0（TS Serial）、TSSEL=0、GPIO7SEL=1へ変更し、TSERRSELは維持します。その後、フルセグ側ならMain1 08 bit0=1、メーカーの `tuning(0,13)`、Sub 72/73/2DとMain1 0D/0E/0Fの固定値設定を含みます。最後のMain1 E8のread→writeは同じレジスタ値の読出し・書戻しで、波形の搬出ではありません。Main2 E8の出力モード設定とも区別します。

既知の生成パターンは、正常受信に依存しない取得経路の検証候補です。ただし、メーカーの設定は通常のSPIモードを変更するため、既存SPI FIFOへ生成データが届くかは未確認です。E7だけの変更でメーカー処理を再現したことにはなりません。メーカー処理全体の実機実行やRF固定値の移植はしておらず、IQ取得も未確認です。

TUVL01の既存RAMファームからUARTでE7だけを `00→01→11→21→00` と変更し、各回の読戻しと有限長SPI取得を比較しました。出力モード・RF設定・再選局・Main1 08は変更していません。最初と最後の通常値では各128枠・24064バイトを取得し、UART輸送CRCが一致しました。途中の3設定は各2000回のFIFO emptyで0バイト、overrun/underrun/reservedは0でした。E7の復帰とUART応答、I2Cエラー0を確認しました。

この切り分けでは、E7だけの変更によって通常SPI FIFOからの取得が止まりました。メーカーの生成パターンがSPIへ届くことは証明できず、生成機能の不存在も意味しません。最初と最後の通常データも各128枠中127枠にTEIがあり、正常TSの基準には使えません。0バイトの結果を有効な波形やIQとして扱いません。

続いて、メーカー処理がE7と併せて設定するMain1 08 bit0を追加しました。通常SPIモードのまま、E7=`01`→`11`→`21`、08 bit0=`1`を維持する順序では、各128枠・24064バイトを取得できました。AA設定は全バイト`AA`、FF設定は全バイト`FF`で、UART輸送CRCも一致しました。巡回設定のデータは変化しますが、正確な生成規則は未確定です。これはMN885521の内部試験データ源から既存SPI・RAM・UARTへの搬出を確認した結果で、IQ信号の取得ではありません。

既存RAMファームで選局・通常TS設定・SPI初期化を済ませ、次のホストツールで比較手順を実行できます。新たなファームアップロードは不要です。成功時の搬出は確認していますが、連続実行時の生成初期化条件は未解決です。

```
python tools/tuner_pattern_capture.py --port COMx --log logs/pattern.bin --output-dir logs/pattern-capture
```

ツールは既知のフルセグ/SPI状態とフレームロックを確認し、通常→巡回→AA→FF→通常を有限長取得します。E7は全バイト、08はbit0のみを変更し、書込み読戻し・輸送CRC・AA/FF全バイト一致・設定復帰を検証します。失敗時も両レジスタの復帰を試み、`report.json`に結果を保存します。RF・再選局・port mode・Flashは変更しません。メーカー処理全体の移植ではなく、実測で確認した順序です。AAから直接始めた別試験は0バイトだったため、巡回から始める順序を省略できるとは確認していません。08 bit0の正式な機能名、順序依存の原因、IQ source mux・形式・レートは未確定です。通常へ戻したデータには引き続き多数の受信エラーがあり、有効な放送TSの検証とは区別します。

同ツールの初回成功ではAA/FF各24064バイトが全バイト一致しましたが、続けた再試験では巡回・AAとも0バイトで、ツールはパターン不一致として終了しました。復帰読戻しに成功し、その後の通常FIFOから再び128枠を取得しました。したがって、設定値だけで常に再現する方法はまだ確立していません。生成データが搬出できた事実と、連続実行時の初期化不足を併せて記録しています。

メーカー末尾のMain1 E8同値read/writeを各試験値の設定後に追加した比較も、巡回・AAが各2000回emptyで0バイトでした。その後、通常の再初期化・14ch再選局を別コマンドで行った試験は巡回・AA・FFすべて24064バイトを取得し、AA/FF全バイト一致と復帰を確認しました。ただし、再初期化を組み込んだ次の試験は再び0バイトでした。E8同値書戻し単独でも、通常再初期化単独でも、常時成功する条件は確立していません。

`--reinitialize` を追加すると、測定前に既存の通常SERVE初期化・既定選局を実行し、その結果を `report.json` に残します。この指定は選局状態を変更し、復帰先は初期化後の通常状態です。省略時は現在の選局を維持します。SERVEの `ready` は正常な放送TSや生成機能の成功を保証せず、同オプションも生成初期化の解決策としては未確認です。最終通常FIFOの取得・CRC・設定復帰は確認しましたが、128枠中127枠のTEIが残っています。

成功例と失敗例の取得前後に19レジスタ（Sub 72/73/2D、Main1 0D/0E/0F/08/E7/E8/97/D6/D7/DA/DB/ED/F3、Main2 E8/F8/F2）を読戻して比較しました。通常・巡回・AAの各条件で、成功例と失敗例の設定値はすべて一致しました。通常値はSub 72/73=`13/51`、Main1 0D/0E/0F=`B9/61/E6`で、メーカー試験の固定値とは異なります。この比較だけで、その差が原因か、内部状態・タイミングが原因かは判定できません。

`--snapshot-state` を指定すると、各取得の前後にこの19レジスタを読み、`report.json` の `observations` へ保存します。読み出しによるUARTの待ち時間が加わり、同時刻の測定でもありません。成功・失敗の一致はこの19レジスタの読戻し範囲に限られ、全内部状態の一致を意味しません。IRQや内部メモリ全体を走査する機能ではありません。

### GPIO読出しの自己試験

通常SPI設定で `python tools/uart.py tuner-pin-selftest --port COMx --log logs/pin-selftest.bin`（直接UARTなら `,`）を実行できます。DMA/RSPI停止、既知の端子設定、E8/F8の通常SPIモード、E7の試験停止、PD5のチップ選択が非アクティブであることを確認します。PD4だけをGPIO出力にしてSPIクロックのLow/Highを16点比較し、端子機能・方向・出力ラッチを戻します。各点でチップ選択の非アクティブも確認し、崩れたら試験を打ち切ります。復調器レジスタへの書込みはありません。

実機で3回とも16点すべてのGPIO読戻しが期待値と一致し、E8/F8/E7不変とMCU設定復帰を確認しました。その後のメーカー設定によるピン試験は両caseとも全点Highのままで、SPI FIFO応答も確認しました。これはPD4の既知レベルを読めることの確認です。PD5〜PD7の個別校正、高速入力波形の追従、メーカー試験の出力先やIQ取得は確認していません。

メーカーライブラリの `tunerx_read_reg` は結果を16ビットの配列へ格納しますが、[対応する公開ドライバ](https://github.com/CyanogenMod/android_kernel_htc_msm8994/blob/2af5dee3f9f7226246978aa905dedea75498853c/drivers/media/platform/panasonic/mn885521/tuner_drv_hw.c) は各レジスタのアドレスを1バイトへ変換し、1バイトずつ読みます。APIの構造体や配列が16ビットだからといって、16ビットのIQサンプルや広い内部メモリを読めるわけではありません。この通常レジスタAPIとは別に、内部プログラム窓の読出し方法を確認する必要があります。
